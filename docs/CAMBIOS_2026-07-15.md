## 1. Antes de nada: qué hacer al bajar los cambios

```bash
git pull origin main
cd backend && npm install        # OBLIGATORIO: hay 5 dependencias nuevas
npx prisma generate              # el schema cambio (modelos de facturacion)
npx prisma migrate deploy        # 3 migraciones nuevas
cd ../frontend && npm install && npm run build
```

**Si te saltas `npm install`, todo el módulo de facturación falla** con
`ERR_MODULE_NOT_FOUND`. Las dependencias nuevas son `node-forge`, `xml-crypto`,
`@xmldom/xmldom`, `bwip-js` (timbre PDF417) y `@fastify/multipart`.

**Si te saltas `prisma generate`**, `prisma.factEmpresa` sale `undefined` y los
tests del motor DTE fallan con `Cannot read properties of undefined`.

### Sobre los tests

La suite corre contra **Postgres real, sin mocks**. Los tests de facturación que
tocan base (`facturacion-engine`, `facturacion-db`, `facturacion-routes`)
necesitan la BD de test levantada. Los que no la necesitan dan **27/27**.

Ojo: si tu `.env` apunta al túnel SSH de producción (puerto 55433), los tests
fallan con `SASL: client password must be a string`. Eso es entorno, no código.

## 2. Inventario — el costo ya no es campo abierto

**Commits:** `a68e551`, `777aebf`, `46b6cde`

- "Precio lista" pasó a llamarse **"Precio costo"** en el formulario y el listado.
- El precio costo es **de solo lectura siempre**, incluso al crear. Se define
  únicamente asignando proveedores; el producto nace en costo 0.
- Aviso cuando el producto no tiene proveedores asignados.
- Se limpiaron **29.595 productos** con HTML crudo en las descripciones
  (`<span>`, `<br>`, `&nbsp;`). Script: `backend/scripts/clean-descripciones-html.mjs`.
  Ya aplicado en producción; verificado: 0 productos con HTML restante.

### Hallazgo importante sobre precios (leer antes de tocar esta área)

Se revisó el código PHP del SISGES original (`tmp/legacy_extract/sisgestion/`):

- En el sistema viejo, **el "Precio Costo" era un campo digitado a mano**
  (columna `precio1` de `catalogo2`). No se calculaba desde el proveedor.
- El proveedor era **solo un `<select>` de referencia**; no alimentaba el costo
  ni había historial de precios por proveedor.
- No existía ningún % que generara el precio de venta desde el costo.

**Consecuencia:** la tabla `catalogo.producto_proveedores` está **vacía (0 filas)**
en producción, y **eso NO es una pérdida de migración** — el original tampoco
guardaba esos datos. El costo actual (`precioLista`) es fiel al original.
`recomputeProductoCosteo` (costo ponderado multi-proveedor) es una feature nueva
que hoy corre en vacío por falta de datos.

**Pendiente de negocio:** el cliente pide que el costo venga del proveedor y que
un % genere los demás precios. El motor de cálculo ya existe
(`computeConsultaPrecios` en `backend/src/routes/productos/pricing.js`, usa
`precioLista` + `porcVentaSala`/`porcLicitacion` del proveedor), pero en el
formulario los precios se siguen editando a mano. Además **502 de 778 proveedores
tienen `porcVentaSala` en 0**, así que para esos el motor calcularía precio = costo.
La propuesta acordada es un sistema de **márgenes en cascada**
(producto → categoría → proveedor → default) con override y alertas. **No implementado.**

## 3. Facturación DTE — guía de despacho corregida

**Commit:** `1f5fa58`

El módulo DTE (de Sebastián) está vivo en producción y no duplica nada previo
(no existía lógica SII antes; `DetalleFacturaProveedor` son facturas de *compra*,
cosa distinta).

**Bug corregido:** al emitir una guía de despacho (DTE 52), el modal nunca enviaba
`extra`, así que `TipoDespacho` e `IndTraslado` llegaban `null`. Como `tags()` en
`xmlUtil.js` filtra los null, **ambos campos se omitían del XML en silencio** y el
SII rechazaba la guía — con el folio del CAF **ya consumido** (irrecuperable).

Qué se hizo:
- Catálogos `IND_TRASLADO` / `TIPO_DESPACHO` (códigos oficiales del SII) en
  `backend/src/facturacion/documento.js` y `frontend/src/utils/facturacion.js`.
- Validación en `validateDocumentoInput` (`routes/facturacion/index.js`), puesta
  **antes** de que `emitir()` tome un folio, para no quemarlo.
- Selectores en el modal, visibles solo para tipo 52.
- Overlay mientras carga la venta + aviso si falla (antes el botón parecía muerto).

**Cuidado con esto:** el campo `tipoDespacho` que ya existía en `DespachosPage` es
**texto libre** del despacho interno. **No** es el código numérico del SII. Son
cosas distintas, no confundirlas.

### Pendiente: el permiso `facturacion` no es asignable

Hoy **solo el admin puede facturar**, y no hay forma de dárselo a nadie más:

1. `facturacion` no está en la lista `MODULOS` de `frontend/src/pages/usuarios/UsuariosPage.jsx`.
2. No está en ningún rol de `backend/src/middleware/rbac.js` (admin pasa por el bypass `'*'`).
3. Las rutas usan `allowExtra: false`, que desactiva los permisos extra por usuario.

Puede ser intencional (facturar es sensible), pero hoy ni un cajero podría emitir
una boleta. **Decisión tomada: resolverlo bien dentro del sistema de módulos
asignables, más adelante.**

## 4. Matriz de ventas — contadores operacionales

**Commit:** `ad64ac7`

El legacy mostraba en la barra superior cuántas ventas estaban pendientes de
entrega / entregadas sin pagar / no pagadas. Operaciones usaba esos números para
ver de un vistazo qué faltaba despachar. Nuestra matriz solo tenía KPIs de monto.

- `/matriz-ventas/totales` ahora expone `kpis.operacional` con los tres conteos.
- Tres `KpiCard` clicables que aplican el filtro rápido del mismo nombre; verdes
  cuando el contador está en cero.

**Decisiones:**
- Van **sin filtro de fecha**, como en el legacy: una entrega atrasada de la
  semana pasada sigue pendiente hoy, y filtrarla escondería justo lo que se
  necesita ver.
- Respetan el scope de sucursal del usuario (`userSucursalWhere`).

**Ojo con los estados:** la base usa `'Entregado'` (14.986 filas), **no**
`'Entregada'`. Por eso el filtro contempla ambos: `in: ['Entregado', 'Entregada']`.
Si asumes solo `'Entregada'`, el contador da 0.

Verificado en producción: 569 pendientes de entrega, 97 entregadas no pagadas,
417 no pagadas.

## 5. Despacho: comparación con el legacy

Se verificó el flujo legacy contra el PHP real:

- En el sistema viejo, despacho **no era un módulo aparte**: vivía dentro de la
  Matriz de Ventas, con contadores "Pendiente entrega" y "Entregadas".
- La tabla `despachos` **nunca se escribía** (cero INSERT/UPDATE en todo el
  legacy); solo se leía para mostrar dirección/región/comuna.
- Las guías capturaban **solo** `fecha_guia`, `n_guia`, `n_interno` y `origen`.
- "Eliminar venta" era solo para administradores (`if ($nivel == 1)`).

**Conclusión:** nuestro despacho **no perdió nada del legacy y ganó bastante**.
`GuiaDespacho` tiene los mismos 4 campos más soft-delete, `userMod`,
`motivoEliminacion` y relaciones reales. Y nosotros sí poblamos `Despacho`
(transporte, monto envío, contacto, tracking, parciales), cosa que el legacy no
hacía desde la app.

Esto también **valida el revert de `OrdenTransporte`** (`47df449`): en el legacy
no existía ninguna "orden de transporte", solo guías. `Despacho` ya es el
equivalente moderno y completo.
